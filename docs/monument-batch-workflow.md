# 古迹增量制图操作手册

适用于单处及批量新增古迹。入口规则见 [AGENTS.md](../AGENTS.md)，字段、命令副作用与浏览器流程见 [开发指南](development.md)，图像质量分别遵守 [线稿规范](../assets/research/STYLE.md) 和 [设色流程](../assets/color-research/WORKFLOW.md)。本手册是调度约定，不是新的生成器或自动验收器；不引入框架、API Key 或固定代理分工。

## 当前原型模式

用户要求先验证原型并增加收录量，当前 `scripts/plate-policy.json` 为 `{"mode":"prototype"}`。下文质量目检、技术阈值、由质量问题触发的自动返工与前置验收步骤只适用于严格模式；搜索收口、持续补位、及时落盘、真实来源与执行顺序仍适用。

```text
资料/照片 → 并发线稿 → 保存原件 → 设色 → 尽力去底/转码 → 本地预览 → 用户集中人审
                                                                      ├ 通过：记录用户验收，接入
                                                                      └ 不通过：按用户反馈修正
```

- AI 不反复数层、判风格或淘汰生成稿，不以技术指标自动重画。默认不等待前置线稿人审；用户明确要先看线稿时只暂停对应项。
- 线稿使用 `prototype-matte.py` 按灰度生成 alpha、着朝代色，跳过近白边缘与中性笔画拦截。设色继续只去外部连通白底及指定透空；不合适的种子跳过，若去底会删除整图则保留原件副本供人审，不宣称一定透明。
- 转码/汇总跳过 RGB、alpha、尺寸等质量拒绝；图片可先进入本地待审预览，不等于用户已通过。文件不存在、格式无法解码、编码器失败及输入执行中被修改仍如实报告，不能把这些执行失败记作已交付。
- 同一原件和去底参数的既有设色缓存优先复用，保留原有验收。哈希用于缓存和绑定你实际通过的图片，不作为视觉质量否决。来源、提示词仍保存，不为凑数擅改主体或臆填到访。
- 用户明确通过某些 ID 后才执行下面的记录命令；命令不代表代理可以自行批准。未审仍 `pending_user`。这次流程调整不批准历史失败稿，也不重画既有图。

```bash
# 只填写用户明确通过的真实 ID；line 用于用户选择提前审线稿的情况。
node scripts/record-plate-review.mjs color <id> [<id> ...]
python3 -B scripts/prepare-colored-avif.py
node scripts/collect-colored-plates.mjs --require-complete
```

只要用户验收与当前原件/PNG/AVIF 哈希一致，就标为 `approved_user`，不再由技术质量阈值二次否决。图片改变后需重新人审。

恢复严格模式：将配置的 `mode` 改为 `strict`，或依次对线稿、转码、汇总命令加 `--strict`。`white-matte.py` 及其严格回归测试保留；原型使用独立处理器，避免改动严格处理器哈希而重做旧图。生产批次不再以完整审图/像素回归作为原型交付门槛；修改代码时仍运行相关自动测试。

## 1. 开工：先准备一批就绪项

1. 执行 `git status --short --branch`，确认当前任务分支、已有改动及本地素材。检查同名、别名和既有 ID；能复用的已核验图版不重画。
   中国古迹拟名单先从[官方国保名单与选目规则](national-protection.md)按省筛出候选，结合地域、时代、类型缺口与资料就绪程度排序；国保不是唯一收录门槛，不把批次当成质量排名。批次与所绘主体能核实就登记，未确认则不贴标签、继续其他就绪环节。
2. 在 `assets/research/<batch>-plan.md` 保存本批计划，使用下节模板。`<batch>` 是本次唯一批次名，不复用历史批次的授权、路径和 worker。此文件仅用于调度与恢复，生成器仍读取现有逐图 JSON 和 `queue.json`。
3. 集中准备各项的主体、年代证据、照片、结构计数和材质观察；将可立即生成的项置为 `ready`。不必等难项的资料全部查完才开第一轮生成。
4. 从统一提示词一次性准备就绪项的线稿记录和设色草稿，复用同一实拍及风格样本；生成前实际查看输入。设色输入中的最终线稿只能在该线稿核验后确定。

### 可复制的批次计划

填写真实值；未知项明确写未知。时间使用带时区的 ISO 8601；表格可以按批次规模增加行。

```markdown
# 本批新增计划

- 批次名：
- 用户约定范围及分支：
- started_at：
- 基线来源：当前 SITES、队列及 AVIF 清单（记录实际 ID 集合/数量）
- 候选来源：所参考的官方国保批次名单 / 非国保候选依据；每项记录正式单位名、批次、所绘主体对应范围及来源（未确认写未确认）
- 生图起始并发目标：8（线稿与设色合计）；已知工具硬限制更低时遵守限制
- 本次交付范围：本地 / 用户明确要求的发布目标

| id | 所绘主体/范围、年代依据 | 已查看照片及来源 | 结构检查点、材质色 | 阶段 | 生成次数 | 下一步/阻塞原因 |
| --- | --- | --- | --- | --- | --- | --- |

## 在途及结果记录

| id | 线稿/设色 | 工具返回的任务或调用标识 | started_at | completed_at（未知则留空） | received_at | 原件路径 | 结果/失败原因/下次策略 |

## 最终交付

- finished_at、墙钟耗时：
- 生成调用总数、返工数；服务耗时（工具可核对时填写，否则写未知）：
- 峰值在途数量、最终有效并发、降档原因及服务失败数：
- 阶段时间窗及超预算原因；用户等待/服务异常单列：
- 新增、复用、阻塞、待用户审图的 ID：
- 实际检查命令及结果、浏览器检查范围、未验证项：

```

阶段采用 `ready → line_running → line_reviewed → color_running → color_reviewed → delivery_ready`；资料或质量问题可转 `blocked` 并写明恢复条件。这里的阶段不替代逐图 JSON 的状态，也不代表 `approved_user`。就绪、失败和在途项必须能从落盘文件恢复，不能只保存在代理内存中。

## 2. 资料搜索：限时收口，不降低证据要求

- 优先查看已有素材和研究记录，再查文博机构或 Wikimedia Commons。通常一张可靠主体照片加一条年代来源就足以开始；第二张只补被遮挡的结构、计数或颜色，不堆积同角度候选。
- 默认每处首轮主动搜索最多 3 分钟或 2 轮查询，以先到者为准。约十处的首轮资料准备预算为 15 分钟；这是调度检查点，不是合格证据的替代。工具卡住时先记录请求，使用正常可用的其他来源，不绕过访问限制。
- 照片能确认主体、约定范围、关键结构和材质后立即收口。开间、佛龛层数、桥孔等必须先计数；有歧义时预先裁出同一实拍的关键部位，并记录裁图来源，不编辑结构。
- 达到预算仍缺关键证据：将该项标为 `blocked`，写缺什么及已查来源，继续其他项。改变已约定的整殿/全桥为局部、替换主体或接受结构偏差，须向用户确认；不能为凑数量擅自决定。
- 设色优先复用已核验的日间/普通室内实拍。只有材质或颜色不可辨认时才另查，不为每张设色重复从头搜索。

## 3. 生成调度：独立项并发，依赖项按序

```text
参考与结构检查点就绪 → 线稿生成 → 结构目检 → 该项设色生成 → 设色目检
                          ↘ 其他就绪项并发；完成后及时保存、领取与补位 ↗
所有拟交付项合格 → 集中接入 → 线稿重建 → 设色转码 → 汇总 → 测试/浏览器
```

- 工具支持且没有已知更低硬限制时，起始并发目标为 **8**，线稿与设色合计；就绪任务少于 8 时只发就绪项，多于 8 时持续领取、补位，不预先保守限为 3。8 是本项目的激进调度起点，不是已验证的 imagegen 技术最大值。明确工具硬限制优先，不能绕过。每处每张图独立生成，不将多处拼成一张批次图。
- 待生成线稿与已核验线稿的设色共同进入就绪队列；哪项就绪就推进哪项。不逐处完成全部记录、设色、入库后才启动下一处，也不等待整批线稿齐备才开始设色。
- 用当前工具支持的异步任务或批量调用管理并发，保留真实调用/任务标识；按工具要求保证异步任务不会因执行环境退出而丢失。此处不授权自动启用多代理。用户明确要求多代理时，逐图文件可分工，共享 `sites.js`、队列与生成清单由本次指定的整合者统一维护。
- 生成在途时做其他就绪项的资料、提示词、数据草稿或检查点准备；每次调度先领取已完成结果，再补位。按工具规定等待，不反复空轮询，也不让已生成的原件长期无人领取。
- 工具返回后立即保留原件、复制到记录路径、计算实际 SHA-256，同步逐图 JSON 和计划。失败稿使用明确的 draft 路径保留，不覆盖已核验成品，不丢失真实提示词和输入。
- 每项首次目检只按预先列出的检查点逐项判断：主体/构图、可数结构、完整轮廓、线条或材质、文字、白底。透明处理后再逐图查看交付副本；不能用尺寸、alpha 或文件存在替代目检。
- 结构目检后、提交该项设色前，对线稿原件做去底预检：在临时目录运行 `python3 -B scripts/white-matte.py <原件> <临时PNG> --line-color '#000000'`。白底或中性笔画不合格先纠错，不等全批接入才发现；原件保持不动，禁止放宽阈值凑通过。预检成功仍不能替代结构目检。
- 白底原件仍用内置 imagegen；透明处理、种子与原件哈希规则完全不变。不得用抠图删掉误画的灰墙、实体白材或暗门来伪装结构修复。

### 撞墙后降档，而非事先猜测上限

- **降档信号**：明确的限流（例如工具返回的 429）、并发拒绝或服务过载。先暂停新提交，将并发目标按 `8→4→2→1` 逐档减半，保存错误和调整时间。同一波在途任务因相同限制接连失败只降一次；冷却、恢复后的新调用再次碰限，才继续降档，避免一波错误直接打到 1。
- **冷却与恢复**：优先遵守工具给出的重试时间；没有建议时先冷却 30 秒，再次触墙延长冷却。期间处理结果保存、资料或其他检查，不忙轮询。冷却结束且尚在途数量低于新目标后才补位；不为立即达到低并发而取消已接受的任务。
- **避免重复出图**：超时或连接断开不自动视为并发过高；先查任务状态和实际原件。已接受、结果不确定的任务仍计入在途，不能冷却后直接重发。只有明确未接受或确认失败、无产物时才安排重试。
- **领取路径先确认**：内置工具可能用自然语言返回“保存于目录 as 完整 PNG 路径”。不能用允许跨空格的宽泛正则把这整句当成文件名；优先使用结构化输出路径，文字回退只提取实际 `generated_images/<任务目录>/exec-<生成ID>.png` 文件。复制前确认该文件存在且可解码，随后绑定原件哈希。路径解析或复制失败属于领取执行错误，先修正并领取已有原件，不重新生图，也不把等待领取的间隔记成模型计算耗时。
- **不是撞墙的情况**：结构画错、背景不合格或输入无效按质量返工/输入修复处理，不因此下调并发。账号额度耗尽、鉴权失败或明确禁止使用则停止新生成并报告，不能靠减半反复试。并发降到 1 仍持续明确服务失败时保存现场、报告阻塞，不无限重试。
- **稳定后收口**：降档后的新调用稳定成功，本批采用该有效并发，不反复升降震荡。后续批次读取调整记录；只将工具明确的限制视为硬上限，不把一次暂时过载写成永久技术最大值。不单独生成无关图片做压测，探测随用户授权的实际制图任务进行。

## 4. 返工与超时：第二次失败必须换策略

1. 首稿有具体错误：记录失败原因，进行一次只针对该错误的修正，保持已正确的构图。结构正确的线稿不因设色失败而重画。
2. 修正稿仍出现同一关键错误：禁止原样重试。第三次调用前必须记录新的证据或策略，例如同一实拍裁图、逐带编号、明确柱数与开间对应；只加强语气不算新策略。
3. 每张图默认最多 3 次调用。第三次仍不合格时暂停该项，保留候选并报告需要的资料/用户取舍，继续其他项；进一步重试需要用户明确方向。工具传输失败单独记录；结果不确定时先查在途任务与原件，不直接再生成。
4. 单项连续 5 分钟没有阶段推进时，记录正在搜索、分析、服务等待还是返工，明确下一步并切到可并行的工作。超时不是重新提交仍在运行任务的理由。
5. 当前上下文内已经完整读取的规范、源码与共同模板不反复整篇加载；只读取本次所需字段和差异。新回合、技能或工具重置的阅读要求仍须遵守。共用元数据可集中准备，返回后的原件保存与记录更新合并操作；不为一个已知字段反复启动命令。

预算用于止损和及时报告，绝不授权遗漏来源、放行错误背景或自动接受候选。仍有阻塞项时交付已完成范围并说明未完成项，不把整批宣称为完成。

## 5. 集中接入与验证：先完成写入，再读结果

1. 只接入图像、来源、真实生成记录及目检齐备的 ID。集中更新 `SITES`、`PLACES`、`queue.json.entries/count` 和必要测试覆盖，默认未到访。保留旧 ID、队列特殊入口、个人记录及已通过图版验收。
2. 在仓库根目录依次执行以下命令。每条必须确认退出成功后才进入下一条；返回会话 ID 时继续等待完成，不能认为命令已结束。

```bash
node scripts/prepare-plates.mjs
python3 -B scripts/prepare-colored-avif.py
node scripts/collect-colored-plates.mjs --require-complete
node --test tests/*.test.cjs
python3 -B tests/test_transparency.py
git diff --check
```

3. 线稿生成器可能因 `sites.js` 时间变化重处理旧线稿；不把脚本重处理说成重新 imagegen 出图。设色转码按哈希复用旧图，不手改清单伪造复用。除失败修复或输入确实改变外，每批集中重建一次，不每新增一项全量重跑。
4. 核对 `SITES` 与 `COLORED_PLATES` 的 ID 集合，队列 `entries + excluded` 无遗漏/重复且 `count === entries.length`，`progress.pending` 无意外项；旧交付哈希及用户验收未被无关改写。汇总器的 `--require-complete` 不检测队列外遗漏，不能只调数量断言。
5. 浏览器检查首轮预算为 10 分钟。在独立测试 origin/配置上，核对本批各图请求、图注和深浅底效果；每个新增地区检查筛选与别名搜索，代表项检查详情刷新/Back 和窄屏。逐图目检不能仅抽样；未改共享记录或交互逻辑时不重复整套存储与手势测试，修改了就按开发指南的验证矩阵补查。
6. 页面计数或图片仍旧时，先用一次重新加载及实际响应检查判断缓存；确认缓存后使用隔离预览 origin，或按任务范围更新受影响资源版本，不反复盲目刷新。换端口会改变个人记录的 origin，不清空用户真实存储，也不擅停其他任务服务器。超过检查预算时记录具体异常并进入诊断，不跳过剩余检查。
7. 集中更新用户可见说明和批次交付记录；新图仍为 `pending_user`，逐图技术 `complete` 不代表用户通过。只有当前任务明确要求时才提交代码或发布；被 Git 忽略的图片须单独保管，清单入库不等于素材已经发布。

## 6. 恢复与耗时交付

- 中断后先查 Git、批次计划、在途标识和当前项 JSON；核对原件及哈希。已生成但未审的先审，交付缺失的只补处理；不因汇总进度滞后从头重画。不确定的输出先核验对应关系，不猜测归属。
- 每阶段及每次返工及时记录时间。`completed_at` 用工具可核对的完成时间；只有领取时间时填写 `received_at`，不能将晚领取造成的间隔记作生成服务耗时。
- 报告墙钟起止、生成总数和返工数、服务耗时（已知时）、连续阶段时间窗及超预算原因。线稿与设色、资料与生成可能重叠，累计服务耗时和阶段耗时不能简单相加；主动分析/组织时间也不能全部归为工具等待。
- 以本次实际结果说明新增、复用、阻塞、待审、测试、素材和提交/发布状态；不复制历史批次数量或宣称固定时长保证。效率由收口、并发、止损与可核对记录约束，质量底线不变。
